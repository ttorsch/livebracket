# design-sync notes — livebracket-ds

## Repo shape quirks

- **No build step for this DS.** `components/livebracket-ds/` is plain source
  consumed directly by the Next.js app (JSX imported straight into pages) —
  there's no `dist/`, no `tsc`/`tsup` build, no publishable package. The
  repo's own `package.json` `build` script is `next build` (the whole app),
  which is unrelated.
- **Synthetic `package.json`.** Added `components/livebracket-ds/package.json`
  (name `livebracket-ds`, `main: index.ts`) purely so design-sync's `PKG_DIR`
  resolves to that folder instead of walking up to the repo root. Without it,
  `cssEntry`/`findTypesRoot` resolve against the wrong directory. **Don't
  delete this file** — it's not used by the Next app, only by design-sync.
- **`componentSrcMap` pins all 14 components explicitly** in
  `.design-sync/config.json`, because there's no real `dist/index.d.ts` for
  `exportedNames()` to read (only hand-written sibling `.d.ts` files, no
  aggregating entry). If a new component is added to
  `components/livebracket-ds/index.ts`, it must **also** be added to
  `componentSrcMap` in config.json or the sync won't discover it
  (`[ZERO_MATCH]`/missing from the count).
- **`srcDir: "."`** (relative to the synthetic PKG_DIR above) so the fuzzy
  source-enrichment walk covers every subfolder (`buttons/`, `data-display/`,
  `forms/`, `surfaces/`, `brand/`, `bracket/`, `icons/`) — none of them are
  named `src`/`lib`/`components`, which is what the default heuristic looks
  for.

## Why `_generated.sync.css` exists

The DS's real `components/livebracket-ds/styles.css` is deliberately an
`@import`-only manifest (see its own header comment: "no rules inline") that
pulls in `tokens/{fonts,colors,typography,spacing}.css`. design-sync's
`cssEntry` copies the file **verbatim** into `_ds_bundle.css` — it does not
resolve further `@import`s to sibling files, so pointing `cssEntry` straight
at `styles.css` produced `[CSS_IMPORT_MISSING]`/`[CSS_PLACEHOLDER]` errors.

Fix: `cfg.cssEntry` points at
`components/livebracket-ds/tokens/_generated.sync.css` — a flat, gitignored
concatenation of the four real token files, regenerated by
`.design-sync/regen-css.sh`. **Run that script before every re-sync build.**
The real `styles.css` (used by the actual app) is untouched and stays the
source of truth; the generated file is sync-only scaffolding.

## Playwright/Chromium

Installed fresh into `.ds-sync/node_modules` + the machine's
`~/Library/Caches/ms-playwright` for the render check. Not part of the repo
— a re-sync on a different machine needs `npm i playwright` (in `.ds-sync/`)
+ `npx playwright install chromium` again.

## Known render warns

None currently — the 14/14 render check is fully clean (no `RENDER_THIN`/
`variantsIdentical` triaged as legitimate).

## Substituted assets

`GlassCard`'s `Tones` story and `Logo`'s `OnPhoto` story use a CSS gradient
(the brand's own coral/amber sunset ramp) as a stand-in for photography. The
repo has no shipped photo asset — the old `*.card.html` demo files reference
`../../assets/beach-volleyball.jpg`, which doesn't exist anywhere in the repo
(a dead reference predating this sync, unrelated to it). If a real photo
asset is ever added under `components/livebracket-ds/`, swap it in via
`cfg.extraFonts`-style asset wiring is NOT it — just reference the real image
path directly in the preview `.tsx` and drop the gradient fallback.

## Re-sync risks — what to watch next time

- If `components/livebracket-ds/tokens/*.css` change, re-run
  `.design-sync/regen-css.sh` **before** the build — a stale
  `_generated.sync.css` silently ships old token values.
- If `components/livebracket-ds/package.json` is ever deleted (e.g. by a
  cleanup pass that doesn't know it's sync-only), the build regresses to
  `[ZERO_MATCH]`/wrong `cssEntry` resolution — see "Repo shape quirks" above.
- All 14 preview `.tsx` files in `previews/` were authored end-to-end in one
  pass (not generated) — a future re-sync should carry every grade forward
  (`carried forward`, zero `grade cleared`) unless a component's own source
  or its preview changed. A cleared grade on a no-change re-sync means
  something nondeterministic crept into the build — chase it.
- No provider/context is required by any component (confirmed during preview
  authoring — every component renders from just its own props). If a future
  component needs app-level context (auth, routing), `cfg.provider` will need
  wiring then — nothing today needs it.
